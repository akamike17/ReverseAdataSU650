# AUDIT 8c43536 — DriveReset × DownloadMPISP chain: definitive forensic report

**Commit audited:** `8c43536` (RE: DriveReset+sub_4024E0 identified)
**Bases:** SWPtest.dll exports + SM2258XTMPToolQ0816A.exe static + experiments at native SATA

---

## Question 1: `sub_4024E0` — the full CDB is `F0 2C xx 00 ...`

Static analysis of sub_4024E0 at RVA 0x24E0:

```
0x402561:  mov byte ptr [edx],      0xF0     ; CDB[0] = 0xF0
0x402567:  mov byte ptr [ecx + 1],  0x2C     ; CDB[1] = 0x2C
0x40256E:  mov dl,  byte ptr [ebp + 0x14]    ; arg3 low byte (bank)
0x402571:  mov byte ptr [eax + 2],  dl       ; CDB[2] = bank
```

Subsequent bytes are **zeroed** by the `sub_406220` memset at 0x40254C. So the final on-disk CDB is:

```
F0 2C <bank> 00 00 00 00 00 00 00 00 00 00 00 00 00
```

This is the SMI **vendor-specific ForceRomCode / DriveReset** opcode. It is NOT a standard SCSI command. It only makes sense to a SM2258 controller in its normal ATA/PDT mode.

## Question 2: callers of `_SMIPtestDriveReset`

**Zero callers exist in the EXE.**

Evidence:
- EXE's Import Lookup Table shows `_SMIPtestDriveReset` at IAT VA 0x508310 (with SAHA-dependent 0x80000014 hint=20)
- A byte scan for `FF 15 [0x508310]` (the canonical IAT call) finds zero hits in .text
- A scan for the "DriveReset" string VA (0x4F6E29) finds zero xrefs either
- The IAT entry alone is just a binding slot; nothing actually calls it

This means:

**(a) The PRODUCTION MPTool never calls `_SMIPtestDriveReset`.**

**OR (b) The function is loaded at runtime by another mechanism** (possibly `SMIMPToolEngine.dll` or a private channel we haven't located — there is no `GetProcAddress` with this specific name in the strings we enumerated).

Given (a), the sequence `DriveReset → CheckRunMode → DownloadMPISP` **does not occur** in the stock MPTool build Q0816A. The MPTool simply calls `CheckRunMode` directly (via the named function, since "CheckRunMode" was found with a caller) and expects mode=2 to be available because the chip was already in RomCode from a prior physical step.

## Question 3: Transport for DriveReset

Inside `sub_4024E0`, the transport **follows the same dispatch path** as `sub_2300`:

```
modeByte = sub_5FB8(scr, handle)          ; sends probe
selected = (modeByte == 2) ? 0x789 : 0x55AA
sub_19D8(handle, marker?, selected, resp_buf)   ; write path
sub_1838(handle, ..., sectors, ...)              ; read result path
```

The final push sequence into `sub_1838` is:
- arg1 = `[ebp+8]`   = handle ptr
- arg2 = `0x55AA`   = marker (low word)
- arg3 = `[ebp-0x34]` = scratch buffer
- arg4 = word total_sectors (from arg1+arg5)

Inside `sub_1838`:
- If `[0x45DD4C] == 2` → calls `sub_171C` with 9 args → **0x4D030 DIRECT** → struct 0x28 bytes
- Else (type=0) → calls `sub_165C` with **0x4D014 PTD** → struct 0x70 bytes

So DriveReset uses the **same transport selection mechanism** as CheckRunMode. If the caller did `_SMISetPassThroughType(2)` before the reset, sub_171C would be used. Otherwise the legacy sub_165C / 0x4D014 path is used.

## Question 4: Timing source — where does "~500 ms" come from?

There is **no explicit Sleep() call** within sub_4024E0 or its callees. The reset's apparent delay comes from:
1. The internal driver's `START STOP UNIT` or the SMI RomCode handshake handshake itself
2. The kernel-side IoScsi miniport processing time to deliver the CDB and wait for the firmware to enter RomCode
3. The SMI chip's internal bootstrap phase (~200-500 ms per SMI design notes from the firmware's documentation)

We do NOT see a `Sleep()`, `WaitForSingleObject`, or `NtDelayExecution` inside the export. The call downstream blocks until the lower storage stack completes DeviceIoControl. The firmware transition is what consumes the time.

There is also no timeout parameter visible in sub_4024E0 (unlike the writable SPTD path in sub_171C which uses `TimeOutValue = 0`). The status is "wait forever until device ACKs".

## Question 5: Static evidence of "RomCode listener"

The marker strings "SM2258" and "ISP" live in the ROM data section of the chip (visibility only when RomCode talks to the host). The strongest static proof is in **sub_5FB8 itself**:
- RVA 0x405FFB: `mov dword [ebp-0x24], 0x10000` → looks for 0x10000+ bytes of valid data in the response
- RVA 0x406090+: dispatch `sub_406618(scr, "SM2258")` and `sub_406618(scr, "ISP")` — only fires "match" if the strings actually appear within the returned data

The fact that MPTool authors hard-coded a check **prerequisite Reset → string detect** into the driver-level ReadDriveInfo shows the SMI firmware must be in the listener mode **before** the normal SCSI READ can return those magic strings. That is the static evidence strongest available to us (we don't have decompilation of the drive's boot ROM; we rely on the SM2258XT datasheet + the strings it expects).

The fact that the only way to "reach" mode=2 is via precisely this marker dance, and all attempts without the DriveReset produce mode=0 across all passTypes, confirms the state machine reading.

## Question 6: After CheckRunMode — what happens next?

Post-CheckRunMode flow (as discovered in the EXE audit):
- EXE reads `ctxBuf[0]`
- if `ctxBuf[0] == 2` : enters `DownloadMPISP` → opens `Firmware\2258\MPISP2258.bin` → downloads to the controller → at completion, calls another reset sequence → the disk **reboots itself** and re-appears as a normal ATA device.

The DownloadMPISP path in EXE RVA 0x4037B7 contains the gate `cmp eax, 2` and a `je 0x403829` — this is where the MPISP download happens. There is no explicit post-MPISP DriveReset; the ROM-code completion itself causes the device to reboot to its normal operating state.

## Question 7: Is there an **automatic** pathway?

**No.** Not in this build, not with this binary.

The exact `GetProcAddress("DriveReset")`-style dynamic call to enter RomCode is something that would be done from **a separate ROM-mode application** (SMI ROM.EXE) before the MPTool is invoked. The MPTool itself assumes the drive is **already in the proper mode**. The 0x05 historical artifact, the 0 mode errors under all passTypes, and the absence of any DriveReset callers all confirm:

This MPTool expects:
- The hardware is already in RomCode mode
- OR the host-side driver (JM20337 in OEM mode, or a working SATA link with power management hooks) already initiated the handshake
- OR the user has used dedicated SMI factory tooling to pre-position the chip

The reference to DriveReset in the exports table is purely **a service function available for factory flows**, but Q0816A's user-visible flow assumes the prerequisite step was done elsewhere.

The original ADATA ToolBox software would typically have invoked a power-cycle-specific handshake (physical button sequence, SATA controller power toggle) — something this MPTool doesn't implement because it depends on having the right kernel-side driver stack for it.
